# Control Center GUI 样式、布局与结构优化执行方案

## 1. 目标与范围

面向当前 Go + Gio 原生 Windows GUI，统一页面骨架、视觉层级、组件交互和窄窗口布局，解决截图中出现的信息拥挤、卡片比例失衡、内容裁切和状态表达不清等问题。保留现有深色背景、青色主操作与霓虹强调的产品风格，并保持现有硬件功能和操作语义。

本方案仅规划 `internal/gui` 及其相关 GUI 测试、设计文档的优化；硬件协议、驱动、业务行为与部署方式不在重构范围内。需要改变状态表达时，先核实后端是否能区分相关状态，不根据数值猜测设备状态。

### 分析依据

- 用户提供的九张截图：系统监控、LED 设备、FlexiKey、FlexiCharger、CPU 超频、GPU 超频、电池、节能计划和偏好。
- 当前工作区中的 `internal/gui/gui.go`、`tokens.go`、`theme.go`、`comp.go`、`draw.go`、`page_system.go`、`pages_mid.go`、`pages_hw.go` 和现有 GUI 测试。
- `docs/05-UI设计规范.md` 与 `README.md`。现有设计文档中的版本说明与部分 token 描述存在差异，应在实施时以实际源码和确认后的新规范为准。

**基线说明：**截图与当前工作区源码并非完全一致。例如当前源码部分页面已有 `pageHead`，截图中未见同样的页面标题；因此截图现象是视觉基线，具体成因以当前代码及实际运行复现为准。工作区已有未提交改动，实施时应在其基础上增量修改并保留无关内容。

## 3. 目标界面结构

### 3.1 全局骨架

```text
┌──────────┬──────────────────────────────────────────────┐
│ 导航     │ 标题栏：应用名                       窗口控件 │
│          ├──────────────────────────────────────────────┤
│          │ 设备信息：型号 · CPU · BIOS                  │
│          ├──────────────────────────────────────────────┤
│          │ 页面标题 / 简短说明                状态或操作 │
│          │                                              │
│          │ 主要内容区：按页面类型使用一列或多列卡片     │
│          │                                              │
│          │                             需要时垂直滚动条 │
└──────────┴──────────────────────────────────────────────┘
```

- 保留现有侧栏、折叠入口、标题栏拖动区、窗口按钮和型号信息栏；调整尺寸时确保拖拽区不覆盖按钮命中区域。
- 页面统一具备名称、简短说明和可选状态区。已有 `pageHead` 的页面复用并对齐，避免重复标题。
- 以页面内容区逻辑宽度作为断点依据，默认内容最大宽度建议为 **1440 dp**；较宽窗口下内容左对齐，避免小卡片被过度拉宽。键盘等需要宽度的区域可在同一最大宽度内使用全宽。
- 内容区保留统一内边距和滚动条空间；内容超出可视高度时使用现有 `scrolledPage` 的滚轮与拖动能力，不截掉末尾操作。
- 当前 `grid2` 已有单列降级，实施时在其基础上修正并扩展，不平行创建另一套不兼容的页面布局。

### 3.2 栅格和断点

以下为首轮建议值，最终以组件自然宽度、最小窗口和实测为准；判断单位均为 **dp**，不直接以截图像素或屏幕分辨率判断。

| 内容区可用宽度 | 布局规则 |
|---|---|
| 小于 900 dp | 主要卡片单列；表单两组无法容纳时逐组换行；复杂键盘可在局部水平滚动。 |
| 900–1319 dp | 主要内容按页面需要使用双列，列宽先满足各自最小可用宽度；不满足时提前回退单列。 |
| 1320 dp 及以上 | 主区域可用双列或 12 列栅格；监控类页面主次分区，配置类页面限制表单宽度。 |

- 列间距统一 16 dp，卡片间纵向间距 12–16 dp；计算列宽时显式扣除并绘制对应间距，避免内容丢宽或贴边。
- 表单字段按“标签 / 输入 / 单位或说明”对齐；长标签允许换行，不能以压缩数字框或隐藏单位解决。
- 页面最小窗口由现有 `minWinW` / `minWinH` 确定；对最低尺寸下可用的内容宽度进行实测，不将断点等同于窗口宽度。
- 页面级垂直滚动与复杂内容局部水平滚动应有明确边界；不使用整个页面的横向滚动代替合理换行。

### 3.3 风格与设计令牌

- 维护深蓝黑背景、低对比卡片边框与青色主操作；亮绿表示启用或正常状态，黄色用于温度或提醒，红色用于错误或危险状态。选中态、禁用态还需使用文字、图标或形状辅助表达。
- 在 `tokens.go` 集中定义背景、文本、语义色、间距、字号、圆角、断点、控件最小高度及复杂图形尺寸；清理本次涉及区域内有冲突的硬编码，不做全项目无关格式化。
- 普通正文建议不低于 13 sp，说明文本建议不低于 12 sp；卡片标题、页面标题、关键数值形成稳定层级。数值及单位统一基线，优先使用等宽数字或等宽布局，避免刷新时跳动。
- 常规文字对背景按 WCAG 对比度公式检查，目标不低于 4.5:1；大字目标不低于 3:1。禁用、装饰元素单独处理，并确保其不可用原因可识别。
- 主按钮、次按钮、危险动作、开关、滑块、数字输入、下拉和页内标签分别定义默认、悬停、焦点、按下、禁用状态；常用交互命中高度建议至少 36 dp。
- 选用统一圆角与卡片边框规则，具体数值以 `tokens.go` 最终落地值为唯一来源，同步修订 `docs/05-UI设计规范.md` 中互相矛盾的内容。

## 4. 各页面布局方案

### 4.1 系统监控

- 页面顶部依次展示页面标题、性能模式切换；主内容分为“CPU 与风扇控制”和“监测与设备信息”两组。窄窗时按此顺序纵向排列。
- CPU 仪表、频率、利用率和温度作为一个完整卡片；数值按列对齐，仪表刻度与文字保持在绘制范围内。
- 将风扇模式、静音开关和偏移设置按操作顺序排列；自定义曲线与保存操作放在同一视觉分组。三张曲线在可用宽度不足时改为两列或一列，保证拖拽点、温度及转速标注可辨认。
- 右侧监控图、风扇转速、GPU 与系统信息使用一致的卡片间距；曲线保留单位、图例及空数据状态。
- 保持采样频率和现有风扇命令逻辑；按页面当前数据源核实监控值缺失时的显示。

### 4.2 LED 设备

- 以“灯光设置”和“键盘预览”为主，睡眠计时器作为独立设置卡片；宽窗口下仅在确认布局与事件稳定后并排，否则保留当前单列结构。
- 色环、选区、亮度、灯效与应用操作组成紧凑设置区。亮度滑块限制在适合操作的宽度内，避免跟随超宽容器无限拉长。
- 键盘预览保持完整比例，按键文字、选择边框和颜色分区清晰；空间不足时使用局部横向滚动并提供可见滚动提示，点击位置必须与显示位置一致。
- 当前 `pages_mid.go` 明确记录双栏曾出现跨栏或双绘问题；改为双栏前应先建立可复现测试，验证不再出现双绘或输入错位。颜色、亮度和灯效下发行为保持原样。

### 4.3 FlexiKey

- 将页内“键盘宏 / 统计 / 鼠标宏”标签集中放置，保证当前标签明显且切换后内容位置稳定。
- 配置档、启用状态及快捷键说明放在配置区；键盘槽位区根据最小可用宽度占据剩余空间，空间不足时改为上下排列。
- 保证键盘右侧完整可达；如需要局部横向滚动，要同步处理贴图、裁剪、滚动偏移及点击命中。
- 明确显示配置文件状态与应用结果；保留现有配置档兼容行为和过滤驱动状态，不将未实现能力展示为可编辑功能。

### 4.4 FlexiCharger

- 左侧为充电策略及阈值，右侧为电池当前状态；宽度不足时策略在前、状态在后。
- 三种策略的标题、解释、单选状态对齐；自定义阈值的标签、数值、滑块与单位分组，避免标注散落。
- 当前设备不支持相关状态时，以明确文字说明并展示可用的后续操作；不要绘制暗示真实电量的占位仪表。
- 阈值约束和应用行为沿用既有实现；若原实现缺少校验，先核实业务约束再提出独立修改。

### 4.5 CPU 超频

- 实时状态和功耗/电压分别成卡；倍频分为 P 核、E 核两组，表单按清晰的标签、输入、单位列布局。
- E 核第二列明确编号 9–16，并验证每个输入框与对应数组项的绑定；显示的核心数量或不可用项以当前后端实际能力为依据。
- 保存、恢复操作在设置区域底部统一对齐；控件在窄窗下换行而非遮挡。
- 保留现有确认交互和应用时机；不要仅凭 `0` 判定数据不可用，需结合数据来源和能力状态。

### 4.6 GPU 超频

- 将 GPU 状态与核心/显存偏移配置做成同一内容区的两个相关卡片；每条滑块配名称、当前值及单位。
- 不支持或 NVAPI 未就绪时，依据实际状态显示原因并清晰标示可操作性；如暂不能区分状态，先维持现有行为并记录后端限制。
- 保存与恢复按钮保持一致位置和视觉层级，保留现有命令与持久化路径。

### 4.7 电池

- 电池信息按“容量与循环 / 健康状态”分组；校准说明和操作独立成卡，宽屏并排、窄屏上下排列。
- 无法取得容量、循环数或健康判断依据时显示明确缺失状态；健康标签只在已有数据和判定结果可信时展示。
- 保留当前校准流程、确认方式及硬件前置条件，界面只说明用户需要知道的操作条件和结果。

### 4.8 节能计划

- 实时功耗图表与当前数值构成监控卡片；充放电阈值、调度和重复周期构成设置卡片。
- 两组调度使用一致的“启用 / 开始 / 结束”行结构，时间字段和单位对齐；窄窗时纵向换行。
- 无历史样本时明确显示暂无数据，图表不伪造趋势；保留现有应用、停用和时间同步逻辑。

### 4.9 偏好

- 按“键盘与快捷键 / 显示 / GPU 模式 / 语言”组织为一致的卡片网格；避免各卡片隔着大面积空白。
- 每个设置明确当前值、编辑控件和对应应用动作；重启条件放在 GPU 模式相关操作旁。
- 保留开关、语言和 GPU 模式现有语义与重启流程；调整布局不改变触发时机。

## 6. 执行顺序

### 阶段一：建立基线与复现问题

1. 记录当前工作区已有改动，确认各页面截图与当前源码的差异。
2. 使用项目现有截图工具或可控窗口采集九页基线；记录窗口逻辑尺寸、DPI、侧栏展开状态和硬件能力状态。
3. 复现双栏间距、E 核标签、键盘裁切、曲线拥挤和缺失数据展示；无法复现的截图问题保留为待验证项。
4. 整理现有布局、控件、截图与交互测试，避免破坏已覆盖的历史回归。

### 阶段二：修复公共布局和高优先级错误

1. 修正 `grid2` 列间距与宽度分配，补充断点两侧和最小宽度测试。
2. 修复 E 核第二列编号，验证编号与字段索引一一对应。
3. 统一页面内容宽度、间距与自然高度规则；检查窗口按钮、侧栏、滚动条和缩放。
4. 补齐常见控件的视觉状态和可用尺寸，确保现有事件处理及数据绑定不变。

### 阶段三：重排重点页面与复杂图形

1. 优先处理系统监控、LED 和 FlexiKey：解决高密度布局、键盘图和曲线的裁切与命中。
2. 调整 FlexiCharger、CPU/GPU 超频、电池、节能计划和偏好页面，统一表单与卡片结构。
3. 根据现有数据模型落实可用、不可用、加载和错误显示；需要额外状态来源时单独确认其实现可行性，禁止用占位值冒充真实读数。
4. 检查键盘缓存和 DPI 几何，保证重绘、滚动、选中与点击一致。

### 阶段四：验证与文档同步

1. 执行现有相关测试与必要的新增回归测试，覆盖栅格、编号、图形边界和交互命中。
2. 按下方矩阵采集并检查各页，核对操作结果、滚动、状态与布局。
3. 更新 `docs/05-UI设计规范.md`，记录最终采用的 token、断点、组件状态和页面结构。
4. 汇总已完成项、未能验证的硬件场景和保留问题，不把截图视觉检查描述为硬件功能验证。

## 7. 验证与验收标准

### 7.1 布局与视觉矩阵

| 验证维度 | 建议覆盖 | 通过标准 |
|---|---|---|
| 页面 | 九个导航页面及其主要页内标签 | 页面标题、主要信息、操作控件和末尾内容均可访问。 |
| 窗口 | 当前最小窗口、默认窗口、最大化；另选内容宽度刚好跨越 900 / 1320 dp 的两侧 | 无文字重叠、控件遮挡和无法到达的内容；切换断点不丢失输入状态。 |
| DPI | Windows 100%、125%、150%、200% | 文字、图形、点击区域和滚动条位置一致；无 DPI 引起的裁切或命中偏移。 |
| 滚动 | 鼠标滚轮、滚动条拖动；需要时局部横向滚动 | 可到达首尾内容；页面与局部滚动方向明确，键盘点击和可视位置一致。 |
| 界面状态 | 加载、正常、无数据、失败、不支持、禁用，以实际可构造状态为准 | 状态文字与数据来源一致；不可操作项原因可识别；真实零值不被误判为无数据。 |
| 视觉 | 截图对比及文本对比度检查 | 卡片间距、标题、标签、单位对齐；常规文字达到方案对比度目标。 |

截图中的 1692×1238 像素不能直接换算成逻辑宽度；记录截图时应同时标明窗口 dp、设备像素和缩放比例。

### 7.2 交互与回归

- 页面切换、侧栏折叠、窗口拖动及最小化/最大化/关闭均可用；标题栏按钮与拖动区不冲突。
- 模式切换、输入框、开关、下拉、滑块、键盘选区、曲线拖动和页面滚动的命中与显示一致；焦点和编辑中的值不因刷新丢失。
- E 核 1–16 的可见编号与对应字段索引逐项一致；布局换列不改变绑定对象。
- LED 色环、键盘贴图在尺寸、选中键和各分区颜色变化后正确刷新；不同 DPI 下键位命中准确。
- 所有硬件操作保持原有业务语义、应用时机与结果反馈。真实硬件写入、超频、校准、GPU 切换和重启等验证，应以可用测试设备和明确的测试安排为前提；无法执行时明确标记未验证。
- 优先运行现有 `internal/gui` 布局、渲染和交互测试及相关构建；针对发现的具体回归补充有意义的测试。测试环境、命令结果和未覆盖场景在实施结果中如实记录。

## 8. 交付与完成定义

实施完成后，应交付：

1. 更新后的 GUI 源码与针对实际回归的测试。
2. 与实现一致的 `docs/05-UI设计规范.md`。
3. 九页关键视口的验证记录，以及测试命令、结果和未验证的硬件场景。

完成标准是：P0 问题已修复并有对应验证；九页主要内容在目标窗口和 DPI 下可访问；已验证的交互和硬件语义保持一致；不能验证的场景及原因明确列出。
